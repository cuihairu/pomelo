# 01 · 这是一个怎样的内核

## 文件系统为什么不住在内核里

操作系统教科书把文件系统画在内核里,pomelo 偏不:文件系统和终端是用户态程序,
住在 `servers/`,跟你的 shell 平级。划分的标准只有一条:**每个任务都绕不开的,
才进内核**。

文件系统只有读文件的程序用得上,终端只有想打字的程序用得上,谁少了它们都照活。
但"把消息递给隔壁任务"、"该谁上 CPU 了"这类事,谁都要经过,所以 IPC 和调度
留在内核。把容易出错的代码挡在外面,出事就伤不到核心:fs 怎么坏,内核都在。

pomelo 的内核只做四件事:

| 留在内核里 (kernel/) | 搬到用户态 (servers/, apps/) |
| --- | --- |
| 中断分发 | 文件系统 (servers/fs) |
| 调度 | 终端 (servers/tty) |
| IPC(消息队列) | shell (apps/shell) |
| 系统调用门 | |

这四个机制加起来,19 个文件 765 行。读完 `kernel/` 那一摞,你就读完了内核的
全部;想核对也没关系,本章末尾会告诉你怎么把机器跑起来。

## 宏内核快在哪,微内核稳在哪

把两种设计放在一起看:

| | 宏内核(Linux、FreeBSD) | 微内核(MINIX 3、QNX、pomelo) |
| --- | --- | --- |
| 文件系统、驱动住在哪 | 内核态,共享同一地址空间 | 用户态服务,各自一个任务 |
| 一次 read 的路径 | 函数调用,直达磁盘驱动 | 消息:应用 → IPC → fs 服务 → 回程 |
| 驱动出了空指针 | 整个内核陪葬,机器重启 | 服务崩溃,内核和其他服务无恙 |
| 服务怎么升级 | 重编内核、重启机器 | 重启那个服务就行 |

两边的账各有一本。宏内核快:服务之间就是函数调用,`read()` 从 VFS 走到 ext4
再下到驱动,一路没有消息拷贝,没有上下文切换;三十年的驱动和文件系统都在,
出了问题一条 panic 栈从应用贯到硬件,gdb 一路跟到底。这些是真实的优势,
Linux 统治服务器不是偶然。

代价是信任面。内核态的代码什么都能干,bug 也就什么都能砸:一个显卡驱动的
野指针和调度器平起平坐,同样一行代码能把机器掀翻。内核几千万行,每一行都
分享全部权力,补丁之后通常得重启,因为要换掉的正是内核自己。

微内核把账反过来算。内核小而稳:七百行的内核,能错的地方就那么多,seL4 能做
形式化验证,前提也是内核小到验得动。故障隔离:fs 崩了,内核不死,把 fs 单独
重启一遍,别的任务毫无察觉,MINIX 3 的驱动崩溃自动重启是几十年前的老功能。
模块可替换:第 5 章你会看到,shell 与 fs 之间只有消息,换一个 fs 实现,shell
一行不改。安全面也小:攻击者想进内核,得先穿过四个机制,而磁盘格式解析这种
漏洞重灾区,根本不在内核里。

代价同样明摆着。一次跨服务调用要过两次系统调用、拷一回消息、切两回上下文,
比函数调用慢一个量级;一条"读文件"的逻辑散在几个任务里,断点跟不过去,
得顺着消息看。这是微内核为人诟病的老问题,不是本仓能回避的。

pomelo 选微内核,算的是教学账:目录就是边界,内核与服务一眼分清;四个机制
每个都不足百行,可以逐个手写、逐个读懂;消息路径清晰,适合在纸上画出来。
工程上的取舍(性能换隔离)属于真实系统,第 12 章会告诉你它们差在哪。

## 读一个文件要过几道门

微内核里"应用获得服务"全程长什么样?拿 `cat hello.txt` 走一遍,这是仓库里
真实存在的路径:

```
apps/shell   cmd_cat:fs_open("hello.txt")
   │
   │ sys_send(FS_OPEN)         ← 系统调用门 0x80,唯一的入口
   ▼
kernel/ipc   把消息放进 fs 任务的收件箱,把睡着的 fs 叫醒
   ▼
servers/fs   do_open:查内存里的 inode 表,命中,回一条 {ino, size}
   │
   │ sys_send(shell, 回复)     ← 回程还是一条消息
   ▼
apps/shell   再发 FS_READ,fs 走 ATA 驱动读扇区,数据分批回来
```

值得盯住两点:第一,shell 进 fs 只有一条路,系统调用门 0x80 加消息,没有别的
门;第二,全程没有一次函数调用跨过边界,shell 对磁盘一无所知,fs 也不知道
是谁在读。应用经 IPC 消息获得服务,这就是 servers/ 目录存在的全部理由。

## 一个反直觉之处:本项目的服务并没有真隔离

真正的微内核靠 MMU(分页 + ring3 特权级)把每个服务关进自己的地址空间,
服务访问硬件或发消息都必须经过内核。Pomelo **先不做这一层**:所有服务跑在同一个
地址空间、同一个特权级,靠**纪律**而非硬件来划界,谁都不许直接碰别人的变量,
想请求服务就老老实实发消息。

这叫**逻辑微内核**。它保留了微内核最重要的东西,*结构*;略去了最繁琐的东西,
*机制*。等你读顺了这条消息路径,再去看[第 12 章](/guide/beyond-mmu),
会发现把它升级成硬件隔离需要改的地方少得惊人。上一节说的故障隔离,也要到
那一天才真正兑现。

## 一次按键会经过谁

本书后面每一章都在补全下面这条链路,先给你一张全景图:

```
键盘中断 ──▶ kernel/intr     (内核抓下扫描码)
              │  IRQ 唤醒持有者
              ▼
          servers/tty        (扫描码 → 字符 → 行缓冲)
              ▲  SEND(line)      │
              │                  │ SEND(line)
   apps/shell │                  ▼
   (读一行,查命令表,再发消息) ──▶ servers/fs  (查 inode,读写磁盘块)
```

shell 从头到尾没碰过键盘,也没碰过磁盘:它只会 `SEND` 和 `RECV`。
